# 收件同步放大复盘

日期：2026-09-13

## 观测

- 生产单个同步 run 持续约 61 分钟，记录了 1041 个 `sync_batch`，`elapsed_ms=3674135`，目标 UID 长期为 1567。
- 批次游标不是单调推进：抽样为 batch 1/2/3 的 543/543/575，batch 151/301/451/601/751/901 的 575/575/1183/1023/1151/575。每约 3 秒出现新连接。
- 同期定时创建约 40 次/小时。实现路径中，启用别名创建、重新启用、自动别名确认和别名导入曾按主号删除账号级 `imap_sync_states` 游标；游标缺失时，首次同步会重新建立最近 1024 封邮件的 no-backfill 边界。pending continuation 又会立即开始下一批；每次增量 fetch 都重新建连、LOGIN 和 SELECT。
- 后续用户收到 SMTP `550 5.2.1 user disabled` 退信；独立 IMAP probe 也证实 Apple 收件/认证异常。因而“Apple 曾出现收件/认证异常”有独立运行证据。现有证据仍未证明异常由本项目创建节奏、IMAP 连接或重复同步导致。

以上组合可以解释游标回退和重复扫描/认证放大：别名写操作清掉整个邮箱流的共享游标，已存在主号的重置同步重新扫描尾部窗口。Apple 收件/认证异常虽有独立证据，仍没有因果证据将其归因于本项目。

## 修复与策略

- 新增别名、别名确认/重新启用和导入不再删除账号级 IMAP 游标。业务取舍：新增邮箱不回扫整主号历史，沿用当前游标继续接收后续邮件；邮箱来源/用户名变更仍保留 UID 归属隔离和重置处理。
- Apple 自动计划按主号使用本地预算：滚动 1 小时 18 次、最小间隔 2 分钟。手动批量创建和单次探测不使用本地额度，成功项之间不额外等待，也不修改自动计划或其 Apple 冷却；仍以 Apple 的实际响应为准。自动计划失败及待确认尝试计数；没有额外的每日 20 次限制。后端日额度为 432（18*24 的冗余约束），任务生命周期为 7 天。该保守策略不是 Apple 官方配额保证。
- Apple 明确限流后，自动计划和手动批量任务暂停至少 24 小时；单次手动探测仅返回该次 Apple 结果及其 Retry-After。`auto` 仅选本轮初始通道，不再把 Apple Account 与 iCloud Web 当作可自动轮换的额度池。此次复盘最初采用 5 次/小时、20 次/日、10 分钟间隔；随后按用户要求调整为上一条策略，并隔离手动探测。
- 收件续批已有独立节流：同一主号至少间隔 30 秒；生产每批最多 128 个候选，同一续跑最多 128 批，并对无进展续批延期。认证错误持久熔断已覆盖自动同步、watcher 与 Seen 标记等入口。增量 fetch 连接复用尚未实现；除 IMAP IDLE 通知的长连接外，增量 fetch 仍需重新连接并认证。

## 验收关注点

- 生产同一邮箱游标在单 run 内单调推进；别名创建/导入/确认不会让 `imap_sync_states` 消失。
- 日志关联 `sync_run_id`、batch、cursor、target 和 elapsed，区分 run 累计时长与单批耗时；观察无新邮件时不会产生无进度续跑。
- Apple 限流、本地预算等待、IMAP 认证失败分别呈现。认证失败提示暂停收件同步、更新 App 专用密码并检查邮箱服务状态。
- 本文不记录凭据、会话、邮件内容或其他秘密，也不作 Apple 端封禁归因。
